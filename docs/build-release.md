# Как собрать и выпустить пакет

Работайте в отдельной ветке с полной Git-историей: геометрические проверки
сравнивают результат с сохранёнными авторскими версиями. Требования к инструментам
находятся в [справке пакета](package.md#среда-разработки).

## Проверка изменения

```sh
pnpm install --frozen-lockfile
pnpm verify
```

`pnpm verify` проверяет сборку, геометрию, декларации, состав и размер пакета,
затем запускает тесты. Список команд находится в [package.json](../package.json).
Поддерживаемые комбинации Node и ОС объявлены только в [CI workflow](../.github/workflows/ci.yml).
Проверка его графа охватывает каждую объявленную комбинацию и общий обязательный результат.

Тесты находятся в [test/](../test/): файл называет компонент или границу,
`describe` — проверяемое поведение, отдельный тест — условие и результат.
Например, [anatomy-generation/](../test/anatomy-generation/) проверяет генерацию
семейств: сходство с авторским рисунком и правила заливки. Архивные эксперименты
в `epics/` имеют собственную конфигурацию и не входят в продуктовый прогон.
[Набор Vitest](https://vitest.dev/api/describe) объединяет проверяемое поведение;
[задание CI](https://docs.github.com/en/actions/about-github-actions/understanding-github-actions#jobs)
и [shard](https://vitest.dev/guide/cli#shard) определяют исполнение, а не принадлежность теста.

Для адресной проверки используйте штатную фильтрацию Vitest, без отдельного
списка групп. Команды выполняются из корня репозитория:

```sh
pnpm test anatomy-generation
pnpm test anatomy-generation/arrows -t 'заливку' --reporter=tree
pnpm exec vitest list anatomy-generation
pnpm exec vitest list anatomy-generation/arrows -t 'заливку'
```

Путь выбирает набор, `-t` уточняет полное имя теста, а `tree` показывает
файл → поведение → результат. Такой запуск проверяет только выбранную часть;
полный `pnpm verify` и обязательный итог CI остаются прежними.
`-t` без совпадений может завершиться с кодом 0 и только skipped-тестами.
Проверка состоялась, только если итог показывает непустой выполненный набор.
`vitest list` с теми же фильтрами помогает проверить выбор, но не выполняет тесты.

Для визуальной проверки текущего авторского корпуса выполните:

```sh
node scripts/build-source-atlas.mjs
```

Откройте `preview/source-atlas.html` и сравните авторские Outline/Filled при
16/24/48 px. Решение о приёмке варианта принимается после визуального ревью
и проверки публичного импорта. `pnpm observatory` создаёт
`preview/observatory.html` для сравнения прежней геометрии с compatibility-моделями.

## Сборка и упаковка

```sh
pnpm build
pnpm pack
```

Сборка создаёт статические экспорты, каталог и Glyph IR. Упаковка повторяет
её через `prepack`. Состав пакета задан в [контракте поставки](../release/contract.json).

`pnpm check:package-artifact` устанавливает пакет из чистой сборки в отдельный
тестовый проект. Проверяются ESM-импорты, декларации типов и отказ CommonJS-входов.
Проверка размера охватывает каждый файл контракта.

## Обновление справки

После изменения метаданных или контракта поставки выполните:

```sh
node scripts/check-docs-drift.js --write
node scripts/check-docs-drift.js --check
```

`--write` обновляет `docs/package.md`. `--check` сообщает об отсутствующей или
устаревшей справке без записи в файлы. Генерация останавливается при ошибке
исходного контракта. Переводы строк CRLF допустимы.

Проверка также находит известные противоречия каналу установки в README и
вложенных документах. После генерации просмотрите diff и пояснения к изменённым полям.

## Релиз

Выберите коммит после успешных обязательных проверок и ревью.
Версию определите по [политике совместимости](semver-policy.md).
Тег исходников должен совпадать с `v<package.json#version>`.

После merge дождитесь успешного CI текущего `main` и передайте его run ID:

```sh
gh workflow run release-packages.yml --ref main -f ci_run_id=<successful-main-run>
```

Workflow продвигает уже проверенные npm, Maven и catalog artifacts этого коммита.
Он проверяет все ссылки `.module`, SHA-256 и принадлежность файлов репозиторию;
публикует source tag `v<version>` и отдельный parentless Maven tag
`maven-compose-v<version>`. Бинарные файлы не добавляются в source-ветку.
Версия берётся из выбранного коммита; чужой, незавершённый, PR-run или CI
другого коммита не подходит. SHA запуска выпуска совпадает с проверенным SHA,
чтобы npm provenance указывала на правильные исходники.

После публикации отдельный headless consumer устанавливает
`pics.lab:icons-compose:<version>` по публичному адресу, с пустым Gradle cache.
Существующий [workflow dist](../.github/workflows/release-dist.yml) выпускает
JavaScript tag `v<version>-dist`.
Npm Trusted Publishing публикует тот же tarball, который прошёл установленный
browser consumer в CI. Отдельный consumer с пустым cache устанавливает публичную
npm-версию; её integrity должна совпасть с проверенными байтами. Затем GitHub
release получает Maven ZIP, самостоятельный каталог и `SHA256SUMS.txt`.
Повтор сохраняет существующие теги и проверяет байты уже загруженных assets;
несовпадающий выпуск требует новой версии.

В настройках npm-пакета `@labpics/icons` Trusted Publisher должен разрешать
`npm publish` для GitHub organization `Labpics-Team`, repository `lab-icons`,
workflow filename `release-packages.yml`. Долгоживущий токен не требуется.
Первую такую привязку добавляет пользователь с правами на npm-пакет;
[инструкция npm](https://docs.npmjs.com/trusted-publishers/).

Каталог распаковывается непосредственно в `/icons/`: `index.html` лежит в корне
архива. Для native используйте Maven URL из [справки Compose](../native/compose/README.md).
Это тот же способ доставки, что уже применяется в Motion Compose 0.1.0.

## Исправление ошибки

До публикации исправьте PR и повторите проверки. Для опубликованного пакета
подготовьте новую версию. Содержимое прежней версии сохраняется, а потребители
переходят на исправление при обновлении зависимости.
