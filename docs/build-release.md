# Как собрать и выпустить пакет

Работайте в отдельной ветке и используйте версии инструментов из
[генерируемой справки](package.md#среда-разработки). Геометрические проверки
используют сохранённые авторские версии, поэтому checkout должен содержать
необходимую Git-историю, а не только рабочие файлы.

## Проверка изменения

```sh
pnpm install --frozen-lockfile
pnpm verify
```

Полный состав команд принадлежит `package.json#scripts.verify`.
Проверка включает сборку, геометрические инварианты, сравнение деклараций,
контроль поставки, размеров и тесты. Здесь не поддерживается её вторая копия.

Для просмотра геометрических отклонений:

```sh
pnpm observatory
```

Откройте `preview/observatory.html`. Исходник, модель, наложение, топология и
геометрические измерения нужны для ревью конкретного варианта. Сам факт
создания страницы не меняет решение о приёмке в quality policy.

## Сборка и упаковка

```sh
pnpm build
pnpm pack
```

`pnpm build` собирает статические экспорты, обновляет каталог и строит Glyph IR.
`prepack` использует тот же полный вход. Состав публичного пакета принадлежит
[контракту поставки](../release/contract.json), а не содержимому старого `dist/`.

`pnpm check:package-artifact` проверяет реальную упаковку из чистых исходников,
установку артефакта в отдельного потребителя, ESM-входы, декларации типов и
закрытую CommonJS-поверхность. Проверка размера должна охватывать каждый файл
контракта; числовые ограничения принадлежат соответствующим машинным бюджетам.

## Обновление справки

После изменения метаданных или контракта поставки выполните:

```sh
node scripts/check-docs-drift.js --write
node scripts/check-docs-drift.js --check
```

Команда записи меняет только производную `docs/package.md`. Команда проверки
не исправляет файлы: она отклоняет отсутствующую, устаревшую или вручную
изменённую проекцию. Некорректный исходный контракт нельзя исправить
регенерацией справки. Локальные переводы строк CRLF допустимы.

Этот контроль также обнаруживает известные противоречия каналам установки в
README и вложенных Markdown-документах. Он не проверяет смысл всей прозы:
научные обоснования, инструкции и границы возможностей требуют ревью.

## Релиз

Релиз выполняется после прохождения обязательных удалённых проверок и
независимого ревью. Класс изменения определяется
[политикой совместимости](semver-policy.md). Не публикуйте рабочую ветку как
готовый выпуск.

Source tag должен совпадать с `v<package.json#version>`. В Bash из корня
проверенного checkout:

```sh
version=$(git show HEAD:package.json | node --input-type=module -e 'import { readFileSync } from "node:fs"; console.log(JSON.parse(readFileSync(0, "utf8")).version)')
git tag "v$version" HEAD
git push origin "v$version"
```

Правила приёма тега и построения артефактного тега задаёт
[release workflow](../.github/workflows/release-dist.yml). Повторное использование
существующего тега допустимо только после проверки его происхождения и байтов
относительно чистой сборки. Не удаляйте и не передвигайте опубликованный тег.

Публикация конкретной версии в npm требует отдельной проверки реестра.
Успех сборки, наличие `publishConfig` или артефактного Git-тега не заменяют её.

## Исправление ошибки

До публикации исправьте изменение в PR и повторите проверки. После публикации
подготовьте новый исправляющий выпуск; нельзя обещать откат переустановки у
внешних потребителей или заменять байты уже опубликованной версии.
