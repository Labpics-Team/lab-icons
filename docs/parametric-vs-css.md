# Параметрика vs CSS/WAAPI — ADR (r2 DOC-01)

## Вопрос

Аффинные трансформации и opacity выразимы чистым CSS/WAAPI без моделей.
Зачем библиотеке параметрическое ядро (`glyph()`, оси, анатомия)?

## Решение: параметрика — для того, что CSS не выражает

CSS/WAAPI трансформирует **готовый контур целиком**. Четыре способности
требуют пересчёта самой геометрии и покупаются только параметрикой:

1. **Weight на filled-формах.** CSS `stroke-width` работает лишь на
   stroke-контурах; наши filled-варианты — заливки, их «вес» = смещение
   кромки по нормали с сохранением counters и негативного пространства.
2. **Corner-ось.** Скругление угла — замена геометрии узла (дуга/сквиркл
   вместо излома), а не масштаб. `border-radius` не существует для path.
3. **Opsz (оптический размер).** Малый кегль требует других пропорций
   (толще штрих, шире counters) — это другой контур, не transform.
4. **Per-part motion.** Смысловой жест двигает именованную часть
   (стрелка часов, клин play) вокруг её pivot; CSS видит один path без
   частей. Части с pivot существуют только в анатомии.

## Что параметрика НЕ делает

Целоглифовые rotate/scale/translate/fade потребитель выражает CSS/WAAPI
поверх статического SVG — библиотека не оборачивает то, что платформа
делает лучше. Motion-ядро библиотеки описывает только смысловые жесты
частей (см. `lifecycle.md`, capability boundary в `anatomy-model.md`).

## Отклонённые альтернативы

- **Всё на CSS + N статических вариантов** (по варианту на комбинацию
  осей): комбинаторика 3 осей × дискретные значения × 476 файлов =
  тысячи артефактов, дрейф между ними не контролируем гейтами.
- **Вариативный шрифт (glyf + gvar)**: оси бесплатно, но иконки теряют
  многоцветность/слои, part-семантику и morph-контракты; toolchain
  шрифта не даёт наших инвариантов (ink-weight, ring-canon, topology).
- **Runtime-морфинг библиотекой (flubber-класс)**: интерполяция без
  топологического контракта даёт «кашу» на несовместимых контурах —
  против этого стоит topologySignature.
